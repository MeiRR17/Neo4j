# v0.12.1 — Signed, bounded read-only research run receipt (NEO-ONLY DRAFT)

## Operational use

The v0.12.0 operator-only `/v1/research/agent-tools/plan` endpoint provides an **unkeyed SHA256** request checkpoint. A checkpoint catches accidental changes to the planned operation, parameters and read budget but does **not authenticate an execution**. v0.12.1 adds a separate domain-separated **HMAC-SHA256 receipt** for exactly one completed read-only tool run, based on the private Neo service token.

The new endpoint is `GET /v1/research/agent-tools/execute/signed`, with the **same** required query fields as v0.12.0 `/execute`: `operation`, `passage_ids`, `query`, `request_checkpoint_sha256` and optional `evidence_ids` (required for `review_dossier`), `limit` and `read_budget`. The supplied checkpoint must be generated by `/plan` **for the identical parameters**. The service validates plan/secret before graph access, performs only the single allowlisted v0.12.0 operation and returns:

- `plan`: typed v0.12.0 plan, with query **hash** and planned 1–3 fixed read operations, never the query text.
- `execution`: typed completed v0.12.0 operation, its original bounded metadata-only result and up to 12 Evidence cards.
- `signed_receipt`: independent v0.12.1 SHA256/HMAC of the canonical exact execution; operation, plan checkpoint, execution SHA256, count, ordered Evidence IDs and the explicit `HOLD` limitations.

The signed response must be treated as **private research metadata**. It includes exact source references and Evidence IDs but no licensed source text, research notes or model-written claims. Store it in an owner-only `0600` JSON file for offline verification; do not paste service tokens into command lines, URLs, logs or GitHub.

## Flag and security requirements

**Default OFF**: both `DVIROS_ENABLE_GROUNDED_CONTEXT=1` and `DVIROS_ENABLE_RESEARCH_TOOL_RUNNER=1` are required. The new endpoint uses the existing private bearer dependency, and the signed-request policy if independently enabled. Invalid or disabled flags cause 503/404 with no graph reads; unknown or repeated query parameters are rejected before dispatch. This does **not** introduce a public or DvirOS end-user authentication route.

HMAC is derived from the existing private local service token. The domain separator is `dviros/neo/read-only-research-run/v0.12.1\n`, independently distinct from all historical review HMAC receipt formats. This provides **local service-key integrity for the supplied metadata run**, not verified reviewer identity, durable job lifecycle, secure long-term key rotation, external timestamping, immutable corpus revision, independent licensed source rights or scholarly validity. A replay of the same query would make fresh graph reads; the signed receipt only attests to the **single completed bounded observed output**.

## Offline verification

After saving the exact `/execute/signed` JSON response into an owner-only private file, verify it without Neo4j, DvirOS, remote providers or any graph queries:

```sh
python scripts/verify_research_tool_receipt_v0121.py \
  --report /private/signed-research-run.json \
  --token-path /private/research-api-token
```

The verifier independently checks the v0.12.0 typed plan and its canonical checkpoint, exact scope/candidate budget, the nested operation-specific response model, coherence of Evidence cards against the original operation result, the result SHA256, and the v0.12.1 domain-separated HMAC. Wrong tokens, approval-field forgery, altered Evidence IDs/source metadata, wrong planned scope or tampered signatures fail closed. It prints **only** a bounded aggregate verification summary; no source refs, private query text, Evidence IDs or token values.

For an offline verifier to be an independent *authority*, it would need separate trusted key custody and authenticated reviewer identities; these are **not** supplied. The same service secret used for bearer authentication must remain confidential and rotated through a future approved process.
